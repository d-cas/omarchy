# Btrfs Snapshot Boot Research: mkinitcpio vs dracut

## Executive Summary

**YES - dracut CAN fully replace mkinitcpio's btrfs-overlayfs functionality for Omarchy Linux.**

Dracut's native 70overlayfs module combined with limine-dracut-support provides equivalent (and potentially superior) snapshot booting capabilities compared to mkinitcpio's btrfs-overlayfs hook. The key difference is that dracut's overlayfs support works automatically when booting read-only btrfs snapshots without requiring manual hook configuration. This makes the migration not only feasible but potentially simpler than the current mkinitcpio setup.

**Migration Impact:** LOW RISK - The functionality is built into dracut and limine-dracut-support already has overlayfs support out-of-the-box. No custom development needed.

## Current mkinitcpio Implementation

### btrfs-overlayfs Hook

**Package:** limine-mkinitcpio-hook (AUR)
- **Maintainer:** Zesko (same developer as limine-snapper-sync)
- **Source:** https://gitlab.com/Zesko/limine-entry-tool
- **License:** GPL3
- **Alternative names:** Also provides `sd-btrfs-overlayfs` for systemd-based initramfs

### What it Does

The btrfs-overlayfs hook enables booting into read-only btrfs snapshots while maintaining system functionality by creating a writable overlay layer in RAM. This is critical because:

1. **Read-only snapshots are immutable** - Snapper creates snapshots as read-only to preserve their integrity
2. **Services require writable directories** - Desktop managers, systemd services, and many applications need to write to `/var`, `/tmp`, `/run`, etc.
3. **Overlayfs provides non-persistent changes** - Any modifications made while booted into a snapshot exist only in RAM and are lost on reboot

### How It Enables Snapshot Booting

**Boot Flow:**
1. Limine bootloader displays snapshot entries (generated by limine-snapper-sync)
2. User selects a snapshot to boot from
3. Kernel boots with snapshot-specific boot parameters
4. mkinitcpio's btrfs-overlayfs hook executes during early boot
5. Hook detects read-only btrfs root filesystem
6. Creates tmpfs workspace in RAM
7. Mounts overlayfs with:
   - **Lower layer:** Read-only snapshot (protected from modifications)
   - **Upper layer:** Tmpfs in RAM (receives all write operations)
   - **Work directory:** Tmpfs for overlayfs internal operations
8. System pivots to the overlayfs mount
9. System boots normally, all changes stored in RAM
10. On reboot, RAM is cleared and snapshot remains pristine

### Integration with limine-snapper-sync

The current Omarchy implementation uses multiple components working together:

**Component Stack:**
- **limine-snapper-sync:** Monitors `/.snapshots` directory and generates Limine boot entries for all Snapper snapshots
- **limine-mkinitcpio-hook:** Provides the btrfs-overlayfs hook AND manages kernel installation/removal for Limine
- **snapper:** Creates and manages btrfs snapshots
- **snap-pac:** Automatically creates pre/post snapshots during pacman updates

**Configuration Files:**

## Dracut's Btrfs Capabilities

### Standard Modules on System

**70btrfs Module - EXISTS: YES**
- **Location:** `/usr/lib/dracut/modules.d/70btrfs/`
- **Purpose:** Basic btrfs support (device scanning, multi-device volumes)
- **Capabilities:**
  - Loads btrfs kernel module
  - Runs `btrfs device scan` during early boot
  - Includes btrfs utilities (btrfs, btrfsck, btrfs-zero-log, btrfstune)
  - Handles multi-device btrfs volumes
- **Snapshot support:** NO - This is just basic filesystem support

**70overlayfs Module - EXISTS: YES**
- **Location:** `/usr/lib/dracut/modules.d/70overlayfs/`
- **Purpose:** Generic overlayfs mounting capability
- **Files:**
  - `module-setup.sh` - Module registration and installation
  - `prepare-overlayfs.sh` - Pre-mount preparation (creates directories, handles reset)
  - `mount-overlayfs.sh` - Actual overlayfs mounting logic
- **Capabilities:**
  - Kernel parameters: `rd.live.overlay.overlayfs=1`, `rd.live.overlay.readonly=1`, `rd.live.overlay.reset=1`
  - Automatic tmpfs creation for upper/work directories
  - Works with block devices and network filesystems
- **When activated:** Responds to kernel parameters, creates overlay on `/run/overlayfs`

**70dmsquash-live-autooverlay Module - EXISTS: YES**
- **Location:** `/usr/lib/dracut/modules.d/70dmsquash-live-autooverlay/`
- **Purpose:** Live CD/USB overlayfs support
- **Snapshot support:** NO - Designed for live media, not btrfs snapshots

### Additional Snapshot-Related Modules

**EndeavourOS Enhancement: eos-dracut**

**Package:** dracut 108_eos-1 (EndeavourOS patched version)
- **Maintainer:** EndeavourOS team
- **Source:** https://github.com/endeavouros-team/PKGBUILDS/tree/master/eos-dracut
- **Enhancement:** Automatic btrfs snapshot overlayfs detection

**eos-dracut 1.2+ Enhancement Files:**
- `module-setup.sh` - Custom dracut module for snapshot overlay
- `snapshot-overlay.sh` - Intelligent btrfs snapshot detection and overlay mounting

**How eos-dracut Enhancement Works:**

The eos-dracut package adds a custom dracut module that:

1. **Automatic Detection:** Checks if root filesystem is a read-only btrfs volume during pre-pivot
2. **Intelligent Overlay Creation:**
   ```bash
   # Pseudocode from snapshot-overlay.sh analysis
   if btrfs_root_is_readonly; then
       create_tmpfs_cowspace
       mount_overlayfs_with_layers(
           lower=/sysroot (read-only snapshot),
           upper=/cowspace (tmpfs),
           work=/cowspace/.overlayfs
       )
   fi
   ```
3. **Zero Configuration Required:** Works automatically without kernel parameters
4. **RAM-based Changes:** All modifications stored in tmpfs, cleared on reboot

**Key Insight:** The eos-dracut approach is SMARTER than mkinitcpio's btrfs-overlayfs because it auto-detects read-only btrfs roots instead of requiring explicit hook ordering in configuration files.

## How openSUSE/Fedora Handle This

### openSUSE Approach

**System:** openSUSE Tumbleweed/Leap with Snapper (the original Snapper distribution)

**Implementation:**
- **Initramfs:** dracut (default for all SUSE distributions since ~2015)
- **Bootloader Integration:** GRUB2 with grub2-mkconfig
- **Snapshot Tool:** Snapper (developed by SUSE)
- **Overlayfs:** Built into dracut with automatic detection

**Boot Menu:**
- GRUB menu entry: "Start bootloader from a read-only snapshot"
- Submenu lists all available snapshots
- Pre/post snapshots created automatically by YaST and Zypper

**Dracut Configuration:**
- No special overlayfs hooks needed
- Standard dracut generates initramfs with btrfs + overlay support
- Snapshots appear in GRUB via `/etc/grub.d/80_suse_btrfs_snapshot` script

**Key Feature:** Completely integrated into the distribution - no AUR packages needed, works out-of-the-box on default installations.

### Fedora Approach

**System:** Fedora 39+ with Btrfs as default filesystem

**Implementation:**
- **Initramfs:** dracut (Fedora is the upstream developer of dracut)
- **Bootloader Integration:** GRUB2 with grub2-mkconfig
- **Snapshot Tool:** User choice (Snapper or Timeshift)
- **Overlayfs:** Requires manual configuration or third-party tools

**Configuration Required:**
1. Install snapper or timeshift
2. Install grub-btrfs (third-party tool by Antynea)
3. Configure `/etc/default/grub-btrfs/config`:
   ```bash
   GRUB_BTRFS_MKCONFIG=/sbin/grub2-mkconfig
   GRUB_BTRFS_SNAPSHOT_KERNEL_PARAMETERS="rd.live.overlay.overlayfs=1"
   ```
4. Enable grub-btrfsd.service to auto-update GRUB on snapshot changes
5. Regenerate GRUB config: `grub2-mkconfig -o /boot/grub2/grub.cfg`

**Kernel Parameters Used:**
- `rd.live.overlay.overlayfs=1` - Enable overlayfs for writable layer
- `rd.live.overlay.readonly=1` - Boot truly read-only (no overlay)
- `rd.live.overlay.size=<size_MiB>` - Set tmpfs size limit (default 32GB)

**Dracut Modules Involved:**
- `90dmsquash-live` - Originally for live media, repurposed for snapshots
- `90overlayfs` - Core overlayfs functionality (added in dracut 58)

**Key Difference from openSUSE:** Fedora doesn't have native Snapper integration like SUSE, requires community tools (grub-btrfs).

### Common Pattern: grub-btrfs

**Project:** https://github.com/Antynea/grub-btrfs
- **Purpose:** Universal GRUB integration for btrfs snapshots
- **Supports:** Snapper, Timeshift, Yabsnap, manual snapshots
- **Initramfs Support:**
  - mkinitcpio: Provides custom `grub-btrfs-overlayfs` hook
  - dracut: Uses kernel parameters (`rd.live.overlay.overlayfs=1`)

**Dracut Integration (from grub-btrfs/initramfs/readme.md):**
```bash
# Set kernel parameters in /etc/default/grub-btrfs/config
GRUB_BTRFS_SNAPSHOT_KERNEL_PARAMETERS="rd.live.overlay.overlayfs=1"

# Regenerate grub config
grub-mkconfig -o /boot/grub/grub.cfg
```

**Key Limitation for Omarchy:** grub-btrfs is designed for GRUB bootloader, not Limine. Omarchy uses limine-snapper-sync instead, which is Limine-specific.

## Migration Recommendation

### Option A: Drop-in Replacement (RECOMMENDED)

**Recommended Approach:** Use limine-dracut-support instead of limine-mkinitcpio-hook.

**Why This Works:**
- limine-dracut-support is a direct equivalent of limine-mkinitcpio-hook
- Both are part of the same limine-entry-tool project by Zesko
- Provides identical functionality: kernel management + snapshot overlayfs
- Works with the same limine-snapper-sync service

**Package Changes Required:**

| Current (mkinitcpio) | New (dracut) | Purpose |
|---------------------|--------------|---------|
| limine-mkinitcpio-hook | limine-dracut-support | Kernel management + overlayfs |
| limine-snapper-sync | limine-snapper-sync | Snapshot sync (UNCHANGED) |
| snapper | snapper | Snapshot creation (UNCHANGED) |
| snap-pac | snap-pac | Auto-snapshots (UNCHANGED) |

**Configuration Changes Required:**

1. **REMOVE:** `/etc/mkinitcpio.conf.d/omarchy_hooks.conf`
   - Dracut doesn't use HOOKS arrays
   - Configuration is module-based and automatic

2. **KEEP:** `/etc/default/limine`
   - Snapshot display settings
   - Boot order preferences
   - All Limine-specific configuration

3. **ADD:** `/etc/dracut.conf.d/omarchy.conf` (create with necessary dracut options)
   ```bash
   # Omarchy-specific dracut configuration
   add_dracutmodules+=" btrfs overlayfs "
   hostonly="yes"
   hostonly_cmdline="no"
   compress="zstd"
   ```

4. **SYSTEMD SERVICES:**
   - KEEP: `limine-snapper-sync.service` (unchanged)
   - ADD: Dracut kernel install hooks (automatic via package)

### Rollback Plan

If snapshot booting breaks during migration, follow this recovery procedure:

#### Emergency Recovery (If System Won't Boot)

**Method 1: Boot from Rescue Media**
1. Boot from Omarchy/Arch live USB
2. Mount encrypted root:
   ```bash
   cryptsetup open /dev/sdXn cryptroot
   mount -o subvol=@ /dev/mapper/cryptroot /mnt
   mount /dev/sdXn /mnt/boot  # EFI partition
   arch-chroot /mnt
   ```
3. Reinstall mkinitcpio and limine-mkinitcpio-hook:
   ```bash
   pacman -S mkinitcpio
   yay -S limine-mkinitcpio-hook
   ```
4. Restore mkinitcpio configuration:
   ```bash
   tee /etc/mkinitcpio.conf.d/omarchy_hooks.conf <<EOF
   HOOKS=(base udev plymouth keyboard autodetect microcode modconf kms keymap consolefont block encrypt filesystems fsck btrfs-overlayfs)
   EOF
   ```
5. Regenerate initramfs:
   ```bash
   mkinitcpio -P
   ```
6. Exit chroot and reboot

**Method 2: Boot from Pre-Migration Snapshot**
1. At Limine menu, select "Snapshots"
2. Choose the "Pre-dracut migration snapshot" created in Phase 1
3. Boot into snapshot
4. From snapshot (with overlayfs), perform rollback:
   ```bash
   sudo snapper -c root rollback
   sudo reboot
   ```
5. System will boot to pre-migration state

#### Systematic Rollback (If Snapshot Boot Fails but System Boots)

1. Remove dracut packages:
   ```bash
   sudo pacman -R dracut
   yay -R limine-dracut-support
   ```

2. Reinstall mkinitcpio stack:
   ```bash
   sudo pacman -S mkinitcpio
   yay -S limine-mkinitcpio-hook
   ```

3. Restore configuration:
   ```bash
   sudo tee /etc/mkinitcpio.conf.d/omarchy_hooks.conf <<EOF
   HOOKS=(base udev plymouth keyboard autodetect microcode modconf kms keymap consolefont block encrypt filesystems fsck btrfs-overlayfs)
   EOF
   ```

4. Remove dracut config:
   ```bash
   sudo rm /etc/dracut.conf.d/omarchy.conf
   ```

5. Regenerate mkinitcpio images:
   ```bash
   sudo mkinitcpio -P
   ```

6. Reboot and verify snapshot boot works

### Known Issues and Mitigations

#### Issue 1: Dracut Regeneration Slow
**Symptom:** `dracut --regenerate-all` takes longer than mkinitcpio
**Cause:** Dracut's hostonly mode analyzes running system
**Mitigation:** Normal behavior, dracut is more thorough
**Workaround:** Use `dracut -f` (non-hostonly) for faster generation if needed

#### Issue 2: Large Initramfs Images
**Symptom:** Dracut images larger than mkinitcpio images
**Cause:** Dracut includes more modules by default
**Mitigation:** Configure `omit_dracutmodules` in `/etc/dracut.conf.d/omarchy.conf`
**Impact:** Minimal - modern systems have plenty of space

#### Issue 3: Different Error Messages
**Symptom:** Boot errors look different from mkinitcpio
**Cause:** Dracut has different logging format
**Mitigation:** Familiarize with dracut error messages
**Resource:** `man dracut.cmdline` for troubleshooting parameters

#### Issue 4: Plymouth Integration
**Symptom:** Splash screen behavior may differ
**Cause:** Dracut's plymouth module works differently
**Mitigation:** Verify plymouth module is enabled in dracut
**Test:** Check `dracut --list-modules | grep plymouth`

## Additional Findings

### Comparison: GRUB vs Limine Snapshot Boot

The research revealed interesting differences in how bootloaders integrate with dracut:

#### GRUB + dracut (openSUSE/Fedora)
- Uses `grub-btrfs` tool to generate snapshot menu entries
- Requires kernel parameter: `rd.live.overlay.overlayfs=1`
- Snapshots appear in GRUB submenu
- Configuration: `/etc/default/grub-btrfs/config`

#### Limine + dracut (Omarchy/EndeavourOS)
- Uses `limine-snapper-sync` to generate snapshot entries
- NO kernel parameters needed (auto-detection via limine-dracut-support)
- Snapshots appear in Limine "Snapshots" menu
- Configuration: `/etc/default/limine`

**Key Advantage:** Limine's approach is cleaner - no kernel parameter manipulation needed.

### Performance Considerations

**RAM Usage:**
- Overlayfs tmpfs defaults to 50% of available RAM (can be limited via `rd.live.overlay.size`)
- Actual usage depends on how many files are modified during snapshot boot
- Typical usage: 100-500MB for a desktop session

**Boot Time:**
- Dracut: Slightly slower initial boot (more thorough hardware detection)
- mkinitcpio: Faster boot (hostonly, minimal modules)
- Difference: Usually < 1 second on modern hardware

**Initramfs Size:**
- mkinitcpio: 15-30 MB typical
- dracut (hostonly): 25-40 MB typical
- dracut (generic): 60-100 MB typical

### Security Implications

**Read-only Snapshots:**
- Provide immutable audit trail
- Prevent tampering with historical system states
- Enable forensic analysis after security incidents

**Overlayfs Temporary Layer:**
- Changes exist only in RAM
- Not persisted to disk
- Lost on power loss or reboot
- Can contain sensitive data in RAM until reboot

**Recommendation:** For security testing, use `rd.live.overlay.readonly=1` to boot truly read-only without overlay.
